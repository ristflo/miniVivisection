# miniVivisection -- Manual

## See your script's data in Rhino while you debug

miniVivisection extends the debugger of Rhino 8's Script Editor. When a script stops at a breakpoint, you can see what its variables hold as geometry in Rhino's viewports, not only as text. You can then change that geometry with Rhino's own tools and write it back into the running script. The values of the code show up where you read it: in the tooltips, and at the ends of lines. Breakpoints can have conditions, hit counts and log messages. A Python prompt, a PowerShell prompt and a Claude chat work on the paused script. Rhino stays usable the whole time, so you can select, measure and run commands while the script waits. Version 0.2.0 is experimental; it was called ScriptEditorWatchViz until October 2026.

---

## Features at a glance

*Kept up to date with every change; the sections below explain each feature.*

**Seeing values (while paused)**
- **V°Watch:** Watched values drawn in Rhino -- points, curves, meshes, planes, vectors -- with name dots; any Python expression as a watch; Interpret as for raw data; selection both ways; Bake; watches "in every thread" (section 3).
- **In the code:** Values in the tooltips and at the ends of lines, "was" for changed values, a value tree, a geometry preview on hover; the editor's Watch tab evaluates expressions; Watch, Bake and Edit in Rhino in the context menus (section 4).
- **Edit in Rhino:** Change a watched value with Rhino's tools and write it back into the paused script, with Undo; Auto edit (section 3).
- **Visualizers:** Your own drawing for your own types (section 7).

**Stopping where you want**
- **Breakpoints with conditions, hit counts and log messages** -- conditions also know `thread_name` and `is_main_thread` (section 5, section 8).
- **Stop once per line:** Continue and Step over finish a line that runs code several times (a comprehension, a one-line loop) (section 5).
- **Break now -- Ctrl+Alt+B:** Pauses a running script at its next line, also on Rhino's UI thread; in your script only, not in imported modules; again after Continue; a sound answers at once -- a soft one when it pauses or stops, an error sound when there's nothing it can (section 8).
- **Run and Debug buttons:** Run always runs plainly, Debug always in the debugger, breakpoint or not (section 8).
- **FreePause:** Rhino stays usable while paused (section 9).
- **The editor stays open** while debugging and for `# async:true` scripts, so V°Threads can be used (section 8).
- **No freeze from another script's pause:** While a script is paused on a thread of its own, a debug run on Rhino's UI thread (another editor, a Grasshopper component) waits with Rhino usable, and goes on once you continue the paused one (section 8).
- **Threads:** V°Threads, "Where is everyone?", the freeze guard for threads (section 8).

**Scripts started from Rhino's command line**
- **RunPythonScript command** (V°Settings): *Stop and record* -- full speed, Ctrl+Alt+B stops the script (an error is recorded too), and the Script Editor then opens it at the line, with the call stack and values of that moment and an explanation; or *Debug* -- runs it in the editor's debugger, the editor invisible until the script pauses (section 8).
- **ScriptEditor Run** gets a Debug=On option (section 8).

**Grasshopper**
- **Three modes for Grasshopper script components** (V°Settings > Grasshopper, or the V° button on Grasshopper's toolbar, which goes round them): *Normal* (V°, gray) -- plain; *Stop and record* (V° with a green Run, the default) -- Ctrl+Alt+B stops a component that hangs; *Always debug* (V° with the Debug icon) -- every recompute runs in the debugger (section 8).
- **Ctrl+Alt+B with a component's editor closed** (Stop and record): Stops it, then opens its editor at the line, with an explanation; Debug runs it again in the debugger (section 8).
- **Hidden editors (Always debug):** Every Python 3 script component gets its script editor out of sight, so Ctrl+Alt+B or a breakpoint pauses it -- not only stops it -- even if you never opened its editor; the editor comes up at the pause (section 8).
- **Editors follow the definition:** Opening another definition, or switching the canvas to another open one, closes the script editors of the one left first (not a paused script's; V°Settings > Grasshopper > *Close script editors when the definition changes*) (section 8).
- **Grasshopper while paused:** Pan, drag and hover on the canvas while a script component is paused; a change elsewhere (a slider, a wire, a Panel) is **computed at once with what is downstream of it** -- downstream of the paused component too, from its last finished run's data -- and everything properly when the pause ends; what depends on the paused component is **marked** (an orange veil, dashed wires: its data most probably isn't right any more); a new solution (a paste, the search box, an Alt-drag copy) waits for the pause to end; deleting is refused until then -- unless the definition is closed (section 8).
- **Wiring without the editor popping up:** A runtime error right after wires were connected or disconnected (a Ctrl+drag) doesn't pause -- the component shows it (section 8).
- **Scripts from a component's script input** (a Panel's text, or a file's path) open in the Script Editor: saving writes back into the Panel (an undo step; refused when the Panel changed meanwhile -- open it again) or the file, and the component recomputes; after Ctrl+Alt+B, at the line where it stopped (section 8).
- **Scripts in Panels shown as code:** A Panel holding a Python or C# script shows it in a monospace font, with line numbers and syntax colors, unwrapped, with a scroll bar along the bottom for long lines; double-click it to edit it right there, as code (or in the Script Editor, from its menu); after Ctrl+Alt+B it opens at the line where it stopped, with what happened; its menu's *Show as* makes any Panel code (Python, C#), rendered Markdown -- double-click it to edit its source, the caret where you clicked --, or plain text. A Panel fed by another (its input connected) shows its data the same way when it opens like Markdown (a heading, a list) or starts with a script's marker line -- *Show as* in its menu decides otherwise. In rendered Markdown a **task box** (`- [ ]`) is clicked like a link: checked or unchecked in the Panel's text (an undo step); how it all looks comes from the Grasshopper **Markdown style** (section 8, section 9).
- **Links in Markdown:** A link to a file -- `[next lesson](gh3_stop_a_hang.gh)`, `[the model](model.3dm)` -- opens it, or, a definition open already, shows it; `[text](gh:Name)` centers the Grasshopper canvas on that component (its nickname) and marks it with a red circle for a moment; `ghview:Name` restores a named canvas view; `rhino:Name` zooms Rhino to that object (its name; it takes about 10 % of the view, a setting) and marks it; `rhinoview:Name` restores a named view of Rhino's (or makes a viewport the active one, by its title); a script -- `[lesson 1](01_watch_geometry.py)`, `script:file.py` -- opens in the Script Editor (not run); web addresses open in the browser. Links are **blue, a line under them** -- as long as the link's words, 10 % of the text high, 15 % under the baseline (the Markdown style's `a { ... }`, section 9; V°Settings > Markdown > *Markdown links in color* off: in the text's color). A file before the name links **from Rhino into Grasshopper and back**: `gh:grasshopper/gh11_markdown_notes.gh#Ring` opens that definition (Grasshopper started for it), `rhino:../00_overview.3dm#Logo` that model. **Click** a link -- in a Panel and in Markdown text in Rhino alike; V°Settings > Markdown > *Markdown links: follow with*: Click, Ctrl+click or Off; a double-click edits; a hint by the mouse says where a link goes and how to follow it. A link that opens a file asks first, unless the file is near the linking one (its folder, or the one above); a `file:` link always asks; nothing opens while a script is paused (section 9).
- **A component with a script input:** Double-click it -- its script and its library input's files open in the Script Editor, the script in front; *Debug the script input* in its menu runs it once in the debugger, pausing at its breakpoints or its first line; under *Always debug* every run does (section 8).
- **async:true in a component:** Its runs go to a thread of their own -- Rhino and Grasshopper stay usable while it computes (section 8).
- **Which branch failed:** Failing runs are named on the component -- run, branch `{0;3}`, item `{0;3}[2]`, line; its right-click menu copies their paths for a Panel (Tree Branch, V°Edit) or debugs exactly that run -- found again by its data (`gh_item == "{0;3}[2]"`) or by its number (`gh_run == 4`); *Debug this component*. The data named is each input's own, as Grasshopper had it for that run (section 8).
- **Which run is paused:** A badge at the top of the code names the component's run, its branch or item and the inputs' paths; conditions know `gh_run`, `gh_branch`, `gh_item` (section 8).
- **Recomputes held back while a script is paused in a solution** -- no "expired during a solution" dialog (section 8).
- **V°Edit component:** Edit Grasshopper geometry in Rhino and feed it back -- items, lists and trees; indices, paths and `{path}[index]` in one input; edits saved with the definition (Grasshopper's Undo, and its save prompt, include them); never saved into the .3dm, hidden or locked too; name dots; Reset sel. / Reset all; *About V°Edit* shows its version (section 9).
- **V°Text component** (its outputs: *Text*, the Rhino text objects, and *Decorators*, the lines and the links' bars (hatches) it's drawn with -- for further use): A Panel's text as Rhino text, as the Panel shows it -- Markdown laid out, a Python or C# script as code with line numbers and syntax colors, plain text; *Height* in points (10 pt by default) or model units, an *Anchor* point at the corner the menu says (top left, top right, bottom left, bottom right), an *Angle*, a *Font* (its *Set one Text* lists the installed fonts); it wraps about as wide as the Panel; outputs the text's aligned bounding rectangle and the anchor; *Bake* makes grouped Rhino objects -- Markdown that edits like `MarkdownText`'s, in place, its links working (section 9).
- **The component's editor:** Run/Debug buttons, and the V pages as buttons in its status bar (section 6).
- **V°Protect component:** Is a definition (or another file) still the original? No inputs or outputs: its files and where their originals go are set in its menu -- by default the definition itself, in *(its name).protect.zip* next to it, or in the definition itself; *Setup*: the files hashed (MD5) and stored in the archive (added to; a changed file replaced; the same name in two folders kept apart), what was stored in its message balloon; *Protect* (its button): it becomes a Button: in front *original* or *modified*, the component green or red (the file on disk, the open definition; the details in its balloon and tooltip), then a gray *Revert* button that puts the original back and opens it again; right-click anywhere on it to go back to setup; a Panel's Markdown shows its state with `{{protected}}` and `{{modified}}`, and `[Revert](protect:revert)` reverts (section 9).
- **Prompts in Grasshopper:** The speech-bubble button on Grasshopper's toolbar opens a window with **V°Claude**, **V°Python** and **V°PowerShell** for the open definition. V°Claude reads the selected components, their data (each item with its facts: coordinates, length, area, volume, closed) and their scripts, and -- with RhinoAI -- places, wires, sets and deletes components, writes scripts and Markdown notes, and looks at the canvas and the Rhino view; **each answer is one undo step** (Ctrl+Z, or `/undo`); or *Read only*. V°Python runs in a paused component's frame and has `ghdoc()`, `ghselected()`, `ghcanvas()`, `ghfind()`; V°PowerShell starts in the definition's folder. An answer stays with its definition: switching the canvas to another one stops it. Settings: on the tab *Grasshopper* (section 9).
- **The tab:** The components are on the tab *miniVivisection*, which reads *V°* when Grasshopper's tabs don't fit (with the mark chosen for the V names).

**Prompts and helpers**
- **V°Python** (in the paused frame), **V°PowerShell**, **V°Claude** (debugging with Claude; code it wants to run waits for your `/run`; **Tab completes its / commands**; RhinoAI for the model, offered for install): Font size with Ctrl+mouse wheel, syntax colors in the Script Editor's colors (section 6).
- **V°Log**, **V°Settings**, **V°Help** (this manual) (section 6).
- **Drop a folder** on the Script Editor: it opens in the editor's Explorer (section 9).
- **The V names:** V°Watch, V°Python, V°Edit, and the plug-in's Grasshopper menu items (*V° Show as*, *V° Debug this component*) -- the mark between V and the name is a setting: ° (the default), |, ∣ (a bar on the line), or either bar with thin spaces (section 6).

Its original kept in an archive next to it (*(its name).protect.zip*) or in the file itself; *Protect* saves it and keeps it; from then on *original* or *modified* (the file on disk, the open model), *Revert* puts the original back and opens it again; *BackToSetup*. In Markdown text, `{{protected}}` shows *protected* or *not protected*, `{{modified}}` *modified*, *not modified* or *not tracked* -- following the state --, and a link `[Revert](protect:revert)` reverts (section 9).
- **Markdown styles (CSS):** How Markdown looks -- sizes, fonts, colors, spacing, bullets, task boxes (drawn, or a character), the quote's bar (`|`), the links' color and line -- is a small CSS file: one for Rhino (`MarkdownText`, V°Text), one for Grasshopper's Panels (V°Settings > Markdown, each with *Edit*, a small editor; the defaults are read-only -- *Save as* makes your own). - **Finding them -- the miniVivisection toolbar** in Rhino: **Manual** (the PDF; right-click: the Markdown in the Script Editor), **Examples** (the overview, your copy), **Examples in Grasshopper** (Grasshopper started, its overview opened), **Lessons folder** (your copies, in Explorer), **Settings** (Rhino's Options, at the miniVivisection page), **MarkdownText**, **ProtectModel**; also as commands: `miniVivisectionManual`, `miniVivisectionExamples`, `miniVivisectionGrasshopperExamples`, `miniVivisectionLessons`, `miniVivisectionSettings`. In Grasshopper the components **V°Examples** (opens its overview), **V°Manual** and **V°Settings** (tab *miniVivisection* > *Help*). V°Settings hides the toolbar (*Rhino*) and the components (*Grasshopper*): *Help, examples and settings* (section 10).

## 1. Getting started

- **Install:** In Rhino 8, `PackageManager`, search *miniVivisection*, tick *Include pre-releases* (it's a beta), *Install* -- or download the package from the web page (`minivivisection-<version>-rh8_36-win.yak`) and drag it onto Rhino 8's window -- then restart Rhino. `PackageManager` offers newer builds, however it was installed, and removes it (*Installed*, miniVivisection, *Uninstall*). A build folder (`bin\Release\net7.0`): drag `miniVivisection.rhp` onto Rhino 8 once. Not both: Rhino would find the plug-in twice. A copy installed from the older zip is removed first -- close Rhino and run `miniVivisection_Remove_Old_Install.cmd` (on the web page, and in the package's `misc` folder), which shows what it found, asks, and keeps a backup; or in `PlugInManager` (miniVivisection, *Uninstall*). The command line then shows `miniVivisection 0.2.0 (build N), <date> loaded (experimental). …`. Rhino 8 only (8.36 or later), on Windows.
- **Where it shows:** The Script Editor's top bar says **miniVivisection 0.2.0 · 2026-10-09 14:05 AST** (version, and when it was built, in your time zone) next to the switches V°AI and V°Debug and the V°Help button. The plug-in adds tabs at the bottom and pages on the left, all named with a **V**.
- **Most features need a paused debugger:** Set a breakpoint (click left of a line number), then debug (F5). Python scripts get everything. C# scripts get watches of plain variable names and conditional breakpoints (a small C# evaluator); they're largely untested.
- **Feature test:** `miniVivisection_Test.py` next to the `.rhp`. Run it for automatic checks, or debug it with the marked breakpoints for a guided tour.
- **Examples:** The **miniVivisection toolbar** in Rhino -- *Examples* opens the overview of all of them, *Lessons folder* your copies --, in Grasshopper the **V°Examples** component (and **V°Manual**, **V°Settings**), and in the Script Editor's left panel **Examples > miniVivisection**; see section 10.

## 3. V°Watch -- drawing values in Rhino

The **V°Watch** tab (bottom) and page (left) list expressions that are drawn in the viewports at every pause.

- **Add:** Type an expression (`crv`, `curves[0]`, `pts[1:3]`) and press Enter. Or right-click a name in the code or a row in Variables and choose **Watch in Rhino**.
- **Each row:** Value, Type and the status *In Rhino* (drawn, nothing to draw, or the error). Rows expand into the value's members, like the Variables tab. Gray rows can't be evaluated right now.
- **Show (eye):** Open and blue means drawn, closed and gray means hidden.
- **Name dots:** Each drawn value has a dot with its name, up and right of it with a tail curving down from its bottom edge to a point at the value, like a speech bubble, so it doesn't cover a point. V°Settings: *Name dots* (on/off), *Name dot offset* (pixels, 0 = on the value), *Name dot opacity* (%), *Name dot pointer* (Tail or a straight Line).
- **Toolbar:** Add, Remove (or Del), Bake, Edit in Rhino, **Auto edit** (ON/OFF), Clear all. The right-click menu: Interpret as, In every thread, Remove, Bake to Rhino, Edit in Rhino.
- **Interpret as** (right-click): How raw data is drawn -- Auto, or e.g. Points, Polyline, Closed polyline, Interpolated curve, lines, anchored vectors, triangles, or Plain data (not drawn); the menu lists what fits the value.
- **Selection both ways:** Selecting a row highlights its geometry in Rhino. Clicking drawn geometry in a viewport selects its row.

**Edit in Rhino.** The value becomes real Rhino objects (layer *Script Editor Watch::Edit*). Move them, drag control points, or use the Gumball, and the change is written back into the paused script. Undo (Ctrl+Z) and Redo write the earlier or later geometry back too. The name dot stays on the edited objects and moves with them. **Auto edit** (on by default) does this for every shown watch at each pause, and right away for a watch added or shown while paused. The objects are removed when the run ends. Python scripts only.

**Bake.** Copies of the drawn geometry go into the document (layer *Script Editor Watch::Baked*).

## 4. In the code, while paused

- **Tooltips:** Hover a name.
    - **First line:** Its value as a line of code, e.g. `count = 5` or `pts = [[0,0,0],[5,0,0],… +2]`.
    - **Facts below it**, in gray, e.g. *4 items* or *closed · degree 3 · length 31.4 · 12 control points*. After a step, *was 4* if the value changed.
    - **Last:** The editor's own text (type and docs).
- **Scope:** Names are read as Python sees them at that line. A global `crv` and a local `crv` show different values.
- **Links in the tooltip:** **Watch in Rhino** · **Edit in Rhino** · **Bake** (for geometry) · **Tree**. Over a class that's called on the line -- `Point3d` in `pts.append(rg.Point3d(ri * math.cos(th), 0, h))` -- also **Watch rg.Point3d(…)**: the whole call, the value it makes, onto V°Watch (computed again at every pause). Only for classes: a watch of `pts.append(...)` would append at every pause. For any other expression, select it and right-click > Watch in Rhino.
- **Tree:** Opens a small window with the value's members, expandable. It stays open while stepping and updates at every pause; Esc closes it.
- **Hover preview:** The geometry under the mouse is drawn in yellow in Rhino, and stays while the mouse is on the tooltip.
- **Values at the ends of lines:** Gray `total = 6, k = 3` after each line of the paused function. After a step, changed values are orange.
- **The editor's Watch tab** evaluates any Python expression (`1+2`, `crv.PointAtStart`), not only plain names.

## 5. Breakpoints with conditions

Right-click a line and choose one of:

| Item | Effect |
|---|---|
| **Breakpoint Condition…** | Pauses only when the expression is true, e.g. `i % 3 == 0` (Python; a small C# subset for C#). |
| **Hit Count…** | `5` (5th hit), `>= 5`, `% 10` (every 10th). Counted from the run's start, after the condition. |
| **Log Message…** | Prints `i={i} total={total}` to the Terminal instead of pausing. |
| **Remove Condition** | Back to a plain breakpoint. |

- **Markers:** A line with a condition shows `◆ if i % 3 == 0` after it. A condition that fails pauses and turns the marker red.
- **The Breakpoints tab** gets a column with the condition and its hits; double-click it to edit.
- **Stepping:** F10 and F11 ignore conditions; only F5 (continue) uses them.
- **Once per line:** A line that runs code several times -- a comprehension like `y = [r.Line for r in rungs]`, a lambda, a one-line loop -- pauses once. Continue and Step over then finish the line instead of stopping for every item (RhinoCode's debugger, like Python's pdb, would). Step into still goes into the comprehension, and a breakpoint with a condition, hit count or log message still decides for every item. V°Settings: *Stop once per line*.

## 6. The other V tabs and pages

- **The names:** miniVivisection's tabs, pages and components are V°Watch, V°Threads, V°Python, V°PowerShell, V°Claude, V°Log, V°Settings, V°Help, V°Edit, V°Text, and the top bar's V°AI and V°Debug. **V°Settings > Editor tabs and pages > *Mark in the V names*** sets what stands between the V and the name: ° (the default), |, ∣ (U+2223: a bar that stays on the line), | or ∣ with thin spaces (V ∣ Watch). It applies to Script Editors opened afterwards, and to V°Edit and V°Text components placed afterwards. This manual writes V°Watch -- to search it, type V° (Alt+0176 on the number pad) or just the name (Watch).
- **V°Python:** A Python prompt in the paused frame, with these commands:
    - `show(value)`, `hide(name)`, `clear()`: draw values in Rhino
    - `bake(value)`: copy values into the document
    - `watch('expr')`: add to V°Watch
    - `edit('expr')`: Edit in Rhino
    - `visualizers()`, `reload_visualizers()`: list or reload visualizers
    - `breakpoints()`: list conditions and their hits
- **V°PowerShell:** A PowerShell prompt (pwsh or Windows PowerShell; path and profile in the settings).
- **V°Claude:** Chat with Claude Code (the `claude` CLI must be installed).
    - **What Claude can do:** Read the paused values and the run's errors, set and clear breakpoints (also with conditions), step and continue, and propose code edits.
    - **Edits while paused** are queued and applied after the run.
    - **RhinoAI:** With it, Claude also works in the Rhino model. When it isn't installed, miniVivisection offers to install it once Rhino has started (V°Settings > Claude: *Offer to install RhinoAI*).
    - **Running Python** (any code in Rhino) asks you first: the code is shown in the tab, with **Run** and **Deny** buttons above the chat and a `> ` prompt -- while Claude's answer is still going on: click Run or Deny, or type `/run` or `/deny`; other messages wait until the answer is done (V°Settings > Claude > *Claude may run Python*: Off / Ask / On; Ask by default). Plain expressions -- a name, an attribute, an index -- are read without asking.
    - **RhinoAI's server** is started for Claude only with V°Settings > Claude > *Start RhinoAI's server for Claude* (it listens without a token); else start it yourself with `MCPStart`.
    - **Claude's edits** go to the script the message was about; with another tab active, they wait.
    - **Slash commands:** `/replace`, `/fix`, `/explain`, `/debug`, `/why`, `/pending`, `/apply`, `/reject`, `/undo [force]`, `/history`, `/allow on|off`, `/run`, `/deny`, `/new`, `/clear`, `/help`. **Tab completes them:** `/ex` + Tab gives `/explain` and a space; when several fit (`/re`), Tab completes as far as they agree and lists them with their help lines; Tab also completes the argument (`/allow o` + Tab lists on|off, `/undo f` gives `/undo force`); Tab on an empty prompt lists every command.
- **In the three prompt tabs:** **Ctrl+mouse wheel** changes the font size (V°Settings > Editor tabs and pages > *Prompt font size*). Typed Python and PowerShell, and code blocks in Claude's answers, are shown in the Script Editor's syntax colors; each tab can switch this off (V°Settings > Editor tabs and pages > *Syntax colors: …*).
- **V°Threads** (tab and left): The script's threads, see section 8.
- **V°Log** (left): What happened, in plain words: runs, pauses, write-backs, warnings, Claude's cost; right-click: Copy, Copy all, Clear, Open log folder.
- **V°Settings** (left, gear): All settings, applied at once, on three tabs: *General* (what the Script Editor and Grasshopper's script components share, and *Markdown*), *Rhino* (watches drawn in Rhino, selection, the RunPythonScript command, FreePause) and *Grasshopper* (script components, Panels, the prompts window) (section 9). The same settings are in **Tools > Options > miniVivisection**.
- **Compact layout** (a Grasshopper component's script editor): The left panel's icons sit in the status bar at the bottom; the V pages get buttons there too, after the editor's own (Search, Templates, Examples, Help). Click one to show its page, again to fold the panel.

## 7. Visualizers -- your own types

Register how your classes are drawn and edited (`import rhinoviv`):

```python
@rhinoviv.visualize(Sensor)
def show_sensor(s):
    return rg.Point3d(s.x, s.y, 0)

@rhinoviv.inverse(Sensor)          # optional: makes it editable in Rhino
def move_sensor(s, edited):
    s.x, s.y = edited.X, edited.Y
```

Visualizer scripts can also be listed in the settings. They load at the first pause of each run, and again when saved.

## 8. Threads

Python scripts that start threads (`threading.Thread`) are debugged thread by thread: a breakpoint pauses the thread that reaches it, and the others stop at their next line until you continue. Add `# async:true` after `#! python 3` so the script runs on a thread of its own and Rhino stays free.

- **V°Threads** (tab and left page): One row per thread -- *paused here*, *stopped by the debugger*, *waiting in join()*, *waiting in with* (a lock), *running* -- with where it is; expand for its stack, double-click for its line.
- **Where is everyone?** (V°Threads): The same while the script runs -- for hangs. When every thread waits, it says *deadlock?*
- **RunPythonScript command** (V°Settings): *Normal* -- `RunPythonScript` runs a script plainly: breakpoints never pause, Ctrl+Alt+B can't stop it. *Stop and record* (the default) -- it still runs plainly, at full speed and without the editor, but **Ctrl+Alt+B stops it**, and where it stopped -- file, line, function, its values -- is recorded; so is an error that ends it. The command line says so. **Open the Script Editor** afterwards (within two hours): it opens the script, goes to the line, and an overlay explains what happened and why, with the call stack and values of that moment (the editor's Call Stack tab fills only while the debugger is paused). No breakpoint is set: run it again with **Debug** and Ctrl+Alt+B pauses it, or click the line's margin to stop there. *Debug* -- a Python 3 script (first line `#! python 3`) opens in the Script Editor and runs in its debugger, also without a breakpoint. The editor stays out of sight while it runs; when a breakpoint or **Ctrl+Alt+B** pauses the script, it comes up at that line and you debug on as usual (Continue, steps, V°Watch...). Scripts without `#! python 3` run in RunPythonScript's old IronPython engine, as before. Each run starts with a line on the command line: Python 2 or 3, and whether Ctrl+Alt+B can pause it (with a hint to switch the option). The Script Editor stays invisible while the script runs (unless you had it open yourself; an editor left open by the last run's pause is hidden again) and comes up in its place only when the script pauses; a run without a pause leaves it minimized.
- **ScriptEditor Run, Debug=On:** Rhino's `ScriptEditor` > Run (also toolbar buttons) has a **Debug** option too: `_-ScriptEditor _Run _Debug=_On "C:\path\script.py"`, the same way. Its default follows *RunPythonScript command*.
- **Grasshopper script components** (V°Settings > Grasshopper, or **the V° button on Grasshopper's toolbar**, right, next to the preview buttons): The button goes round the three modes. *Normal* (V°, gray) -- components run plainly; a component's breakpoints pause only when its solution was started from its script editor's Debug, and Ctrl+Alt+B leaves a component alone. *Stop and record* (V° with a green Run; the default) -- they run as plainly and fast, but Ctrl+Alt+B stops a component that runs (one that hangs), and its editor opens at the line where it was, with an explanation and the values then. *Always debug* (V° with the Debug icon) -- with its script editor open, every recompute (a slider, an input) runs in the debugger, stops at its breakpoints, and Ctrl+Alt+B can pause it. A component's debugger lives in its script editor, so with **Hidden editors for Grasshopper components** (V°Settings > Grasshopper, on by default) Always debug gives every Python 3 script component of the open definitions its editor, out of sight -- one every two seconds, without taking the focus. Its recomputes then run in the debugger too: a breakpoint or **Ctrl+Alt+B pauses it**, and its editor comes up at that line (Continue, Step, Stop as usual). Opening its editor yourself shows it; closed again, it's hidden again; switching to Normal (or the option off) closes the hidden ones, and a deleted component's goes with it. Costs: each one is a Script Editor window (at most 24), and every run is in the debugger -- slower. A definition's very first solution, right when it's opened, runs before its editors are there. Hidden editors stay out of the taskbar and Alt+Tab until they come up. **While a component is paused,** Grasshopper's canvas works: pan, drag components, hover for wire and parameter data, select (Grasshopper itself ignores the mouse while its solution runs); a slider moved or a wire changed meanwhile is **computed at once with what is downstream of it** (V°Settings > Grasshopper > *While paused: compute changes downstream*): the paused component isn't run again -- its outputs show the data of its last finished run, and what is downstream of it computes from that -- and other script components aren't run either (one would start a second debug run); when the pause ends, everything is computed properly. What is downstream of the paused component is **marked** meanwhile: an orange veil and a dashed border on each object, *out of date? (paused upstream)* under it, its wires dashed orange (*While paused: mark what depends on the paused script*). Deleting objects is refused until the pause ends (the paused solution may still need them) -- adding is fine. **Wiring:** a runtime error in the solution right after wires were connected or disconnected -- Ctrl+dragging an input away, say -- doesn't pause, so the editor doesn't come up in the middle of the wiring; the component shows the error, V°Log says why, and recomputing it pauses at the error as usual. **A script from the component's script input** -- its *script* input fed by a Panel's text or a file's path -- has no script editor of its own in Grasshopper. Right-click the component > **V° Edit the script input in the Script Editor**: a path opens that file itself, saving it recomputes the component; a Panel's text opens as a working file, and saving it writes the text back into the Panel (which recomputes the component); text from anywhere else opens as a copy to read. After Ctrl+Alt+B stopped such a component, its script opens by itself at the line where it stopped. Such a script runs plainly, also under Always debug -- running it in the debugger isn't offered yet -- so Ctrl+Alt+B always stops it. Under Always debug, the explanation after the stop (in the Panel, or in the Script Editor for a file) and the component's remark say so. **Ctrl+Alt+B** stops a component that runs plainly first, whatever else is in the debugger: that component is what holds Rhino. **Scripts in Panels:** a Panel holding a Python or C# script shows it as code -- Grasshopper's monospace font, line numbers, syntax colors, and no line wrapping: a long line runs on past the Panel's edge, and a scroll bar along the bottom (drag it, or click the track) brings it into view, next to the Panel's own scroll bar on the right. A Panel counts as a script when its first line is RhinoCode's marker (`#! python 3`, `#! python 2`, `// #! csharp`), when it is connected to a script component's *script* input (that component's language), or when its lines are plainly Python or C# (imports, `def` and `class` lines, `using` lines, statements ending in `;`); notes stay text. **Double-click** it to edit it right there, looking the same: a caret, selection with the mouse or Shift, Ctrl+Z / Ctrl+Y, Ctrl+C / X / V, Enter keeps the indentation (and indents after a `:` in Python, a `{` in C#), Tab and Shift+Tab indent and outdent, Ctrl+/ comments lines in or out, the wheel scrolls (Shift+wheel sideways). Click elsewhere to keep your changes (or Ctrl+Enter, Ctrl+S); Esc drops them. The edit is one step of Grasshopper's Undo. Its right-click menu: **V° Edit the script here**, and **Edit the script in the Script Editor** -- a working file (`.py` or `.cs`) with completion and the rest, saved back into the Panel. A Panel that feeds a script component's *script* input opens as that component's script: the editor knows the component's inputs as variables, and its **Run** and **Debug** compute the component in Grasshopper -- with its inputs, the editor's text taken into the Panel first -- not as a Rhino script, which has none. **Shift+double-click** opens Grasshopper's own text box -- for a script without wrapping, in the monospace font, Tab as four spaces --, **Ctrl+double-click** its dialog. **After Ctrl+Alt+B** stopped a component running a Panel's script, the Panel opens for editing at the line where it stopped, the line marked and an explanation over it (top right): what happened, the run's data, the values then, the call stack -- click it to put it away. The Panel keeps the line marked, with a line about it along its bottom, until its text changes; when the Panel isn't on screen, the Script Editor shows it all. **Show as** (the Panel's menu, saved with the definition): *Autodetect* (the default: code when it's a Python or C# script, rendered when it's plainly Markdown -- two kinds of strong signs such as **bold**, `code`, links, lists, quotes or code fences, or one of them and a # heading -- else as Grasshopper shows it), *Python code* or *C# code* -- any Panel of its own text shown and edited as code, also one nothing marks as a script --, *Markdown (rendered)* -- headings, **bold**, *italic*, `code`, links, lists, quotes, code blocks, tables (as fixed-width text) and rules, drawn in the Panel's width; **double-click** a word and its Markdown source opens in the Panel's editor with the caret at that very place (Enter goes on with a list or a quote; click elsewhere and it's rendered again; its menu also opens it in the Script Editor, which shows Markdown too) --, or *Plain text* for one that should never be -- shown from the top left, as code is, in Grasshopper's font and wrapped as its *Wrap Items* says (Grasshopper centers a Panel's own text), with the same scroll bars. **A component with a script input** -- Grasshopper's own editor is off for it: **double-click it**, and its library input's files (Python or C#, up to 20) and its script open in the Script Editor, the script's tab in front. Its menu's **Open Script Editor** does the same, and **Export Script** saves its script to a file (Grasshopper grays both out for such a component); any script component with a library input has **V° Open the library's files in the Script Editor** in its menu. Only a Panel's own text (no wires into it, Multiline Data on). Options: *Scripts in Panels shown as code* (V°Settings > Grasshopper; on); *Markdown in Panels* (V°Settings > Markdown; on -- off: Markdown Panels show their text as Grasshopper does); *Markdown parser* (V°Settings > Markdown): *Rhino* (the default: Markdig, Rhino's own, as the Script Editor's preview -- CommonMark's rules, nested lists and quotes, task lists with ☐ and ☑, footnotes, tables only with their header rule) or *miniVivisection* (the plug-in's simpler parser). **Threads in a component:** Grasshopper runs a component on Rhino's UI thread, so a breakpoint in one of its threads can't pause (it would freeze Rhino: skipped, V°Log says why). Add `# async:true` to its script (the line after `#! python 3`): its runs -- plain ones, and in the debugger (Always debug, or its editor's Debug) -- then go to a thread of their own, as a Script Editor script's would: Rhino's views and Grasshopper's canvas stay usable while it computes (a long-running component no longer freezes them), and its threads pause, step and show in V°Threads. The definition holds still meanwhile: changes recompute when it's done, deleting waits. Such a script mustn't use Rhino's UI or document where they need the UI thread (V°Settings > Grasshopper > *async:true runs off the UI thread*). Without hidden editors, a component whose editor is closed runs plainly, and Ctrl+Alt+B can only stop it, as in Stop and record. (Before there were three modes, Normal stopped a component on Ctrl+Alt+B: a Normal saved then becomes Stop and record, once.)
- **Run and Debug buttons** in place of the editor's switching Run button: **Run** always runs normally (also with breakpoints), **Debug** always runs in the debugger (also without a breakpoint, so Break now can pause it). While debugging, the editor's own button shows as Continue. F5 is unchanged: Debug with a breakpoint, else Run. The same in a Grasshopper component's script editor: **Run** recomputes the component plainly (breakpoints ignored) -- except with *Always debug* on, which puts every solution in the debugger, Run's too, so Ctrl+Alt+B can pause it; **Debug** recomputes it in the debugger, breakpoint or not. Ctrl+Alt+B pauses a component whose script editor is open (its debugger lives there). With the editor **closed**, Ctrl+Alt+B **stops** a running Python 3 component (its remaining runs and the solution too), then opens its editor at the line it was on, with an overlay explaining it -- press Debug to run it again in the debugger (Ctrl+Alt+B then pauses it); no breakpoint is set.
- **Which branch failed:** A script component runs once per item or branch. When runs fail, a remark on the component names them -- run number, branch `{0;3}`, item `{0;3}[2]`, the line. Its right-click menu: **V° Copy failing branches** / **Copy failing items** (one path per line: paste into a Panel, feed Tree Branch's Path -- or V°Edit's Index -- to isolate exactly that data), **Debug failing run N -- data `{0;3}[2]`** or **-- run number** (its editor opens, a one-time breakpoint at the error line for that run only -- condition `gh_item == "{0;3}[2]"`: the same data, wherever it is in the order now; or `gh_run == N`: the same run number -- and the component recomputes in the debugger), and **Debug this component** (recomputes it in the debugger, pausing at its first line).
- **Which run is paused:** While a script component is paused, a badge at the top of its code shows the run -- *Grasshopper: 'Py3' run 4 · {0;3}[2] · x {0;3}[2], y {0}* (run number, its branch or item, every input's path). V°Log's pause line and V°Python's status line say the same; in V°Python, `ghenv.Component.RunCount` is the run number. While a component's script is paused, Grasshopper must not recompute anything (it would show *Grasshopper breakpoint: ... expired during a solution*), so whatever asks for that then -- a slider, a save, an edit -- is done right after the solution ends; V°Log says so.
- **Break now hotkey: Ctrl+Alt+B** (V°Settings: *Break now hotkey*): Pauses a script running in the debugger at its next line, also one without `async:true`, while Rhino handles no other keys. It works again after Continue, also without breakpoints. A sound answers the key at once -- while a script runs on Rhino's UI thread nothing on screen can change: a soft *asterisk* sound when it pauses or stops something, an error sound when there's nothing it can (V°Log says why). It stops in **your script**: while the script is inside a module it imported, it runs on until it's back in the script (V°Settings: *Break now stops in the script only*).
- **Break now** (V°Threads, or the command `miniVivisection BreakNow`): Pauses at the next line, in any thread; **Break in thread**, in the selected one. It needs a debug run: F5 debugs only when the script has a breakpoint, otherwise it's a plain Run. V°Threads' **Debug** button (the editor's Run > Debug) starts the script in the debugger without one.
- **The editor stays open** while debugging and for `# async:true` scripts (V°Settings: *Keep the Script Editor open while debugging*), so these buttons can be used while the script runs. From Rhino's command line: `miniVivisection BreakNow` (debug runs only: a plain Run isn't in the debugger) and `miniVivisection WhereIsEveryone` (any run: prints each thread and where it is).
- **Conditions and logpoints** know `thread_name`, `thread_id`, `is_main_thread`: `thread_name == 'Worker-3' and i > 5`. Logpoint lines start with their thread, `[Worker-2] i=3`.
- **In Grasshopper,** conditions and logpoints also know the component's run: `gh_run` (its number), `gh_branch` (`"{0;3}"`) and `gh_item` (`"{0;3}[2]"`) -- `gh_item == "{0;3}[2]"` pauses only for that data; a logpoint `run {gh_run} {gh_item}: n={n}` labels every line with its run.
- **In every thread:** While the script runs more than one thread, each watch is also evaluated in the other threads (read only) and drawn once per thread, `pt @Worker-1`; V°Watch > right-click a watch > In every thread turns it off or on for that watch. A thread that hasn't got the name yet is listed as *not (yet) in*. Expand the watch: one row per thread, *(paused thread)* first, then *@Worker-1*, ... with each value; expand a row for its members. Each thread's row has its own eye: hide or show that thread's value, by thread name, kept with the watch. The paused thread's value is labeled `pt @Worker-3 (paused)`. Selecting a row highlights that thread's drawing, clicking a drawing selects its row; Bake works per row, Edit in Rhino for the paused thread only.
- **Freeze guard:** Without `# async:true` the script runs on Rhino's UI thread; a breakpoint in a worker thread would freeze Rhino. That pause is skipped, and the Terminal and V°Log say why. **A Grasshopper component** runs on Rhino's UI thread: its workers' breakpoints are skipped -- unless its script has `# async:true`, which makes its debug runs go to a thread of their own (section 8). `ghpythonlib.parallel.run` computes its first item on the component's own thread: a breakpoint in the function pauses for that one (lesson GH 7).

## 9. More

**V°Edit -- a Grasshopper component** (tab *miniVivisection* > *Debug*). Edit geometry of a definition directly in Rhino:

- **Inputs:** *Geometry* -- an item, a list or a tree. *Index* -- which items, any mix of: **indices** (positions in every branch; negative: from the end -- or per branch with an index **tree**, matched by path), **paths** (`{0;2}` as text, or a Path parameter: only those branches -- all their items, or with indices the items at them), and **path with index** (`{0;2}[3]`: that one item). Nothing connected: item 0.
- **Edit objects:** The items at Index show in Rhino as ordinary objects (**blue**), with a name dot and tail (the plug-in's *Name dot* settings) showing the component's nickname -- rename it and the dots follow at once. The outputs pass the input on unchanged.
- **Edit them in Rhino** with anything -- Gumball, control points, Move, Scale, Rebuild. When you finish, the edited geometry **replaces** its item, and the definition **recomputes from the component on** at once.
- **Outputs, in the input's exact tree:** *Geometry* with your edits in place, and *Edited* -- True or False for every single item.
- **Shown as edited:** The object turns **red-orange**, its dot says *edited*, the component counts the edits, and a balloon on it explains.
- **Kept:** Every later solution uses your edits instead of the incoming items, also when the input changes. The edits are **saved with the .gh file**.
- **Reset sel.** and **Reset all** (the buttons under the component, one above the other): *Reset sel.* drops the edits of the edit objects **selected in Rhino** (orange while one is selected); *Reset all* drops every edit (orange while there are any). The menu also has *Select edit objects in Rhino*, and *About V°Edit…* (its version, build and build time, and the plug-in's). Undo in Rhino back to the input's geometry drops an edit too; Grasshopper's Undo takes back an edit made in Rhino. When the input changes so that another kind of item is at an edited place, the edit isn't used there (a warning on the component names it; Reset all drops it).
- **Preview** (Grasshopper's eye, or the wheel menu's Preview): Grasshopper's own preview of the *Geometry* output, as for other components.
- **Edit objects in Rhino** (menu, checked): Shows or hides the edit objects; **Name dots in Rhino** (menu): their dots. Grasshopper's middle-click wheel menu has fixed buttons only, so these are in the right-click menu.
- The edit objects belong to the component, not to the model: they go away while Grasshopper is minimized or hidden, another definition is on the canvas, or the component is disabled; when it's deleted or the definition closed; and they're never saved into the .3dm -- hidden or locked ones neither (Export Selected exports them, as selected). They don't mark the model as changed.
**V°Text -- a Grasshopper component** (tab *miniVivisection* > *Text*). A Panel's text as Rhino text, the way the Panel shows it:

- **What it makes:** Markdown laid out as `MarkdownText` does (headings, bold, italic, code, lists, task boxes, quotes, code blocks, tables, rules); a Python or C# script as code -- Consolas, the line numbers in a gutter, a frame, each token in its syntax color (a text object per color, lined up); anything else as plain text, its lines kept. *Autodetect (code or Markdown)* (the menu's *Show as*) follows the Panel the text comes from: its own *Show as*, else what it is (a script, Markdown, plain text); or choose Markdown (rendered), Python code, C# code or Plain text.
- **Inputs:** *Text* (connect a Panel; a list is taken as its lines), *Height* -- a paragraph's or a line's text height (Rhino's text height: capital letters), **10 pt** by default: points made the model's units (10 pt = 3.53 mm), or model units (menu: *Sizes in points / in model units*) --, *Anchor* -- a point --, *Angle* -- turned about the anchor in the world's XY plane (radians; *Degrees* in the input's menu) --, and *Width*, the width Markdown and plain text wrap in (0: no wrapping). Without a Width it wraps about as wide as the Panel (plain text only when the Panel wraps): making the Panel wider or narrower, or changing its *Show as*, updates it.
- **Font:** The base font of Markdown and plain text (code stays in Consolas); nothing: the dimension style's. Its right-click *Set one Text* lists the installed fonts, each shown in itself -- type to filter, double-click or OK to take one.
- **The anchor's corner** (menu): *top left* (the default), *top right*, *bottom left*, *bottom right* -- that corner of the text is at the anchor.
- **Outputs:** *Text* -- the Rhino text objects as the component draws them, a token or a part each --, *Decorators* -- everything else it's drawn with: the lines of code frames, rules, quotes' bars, tables' grids -- both placed and turned as the text is (their previews are off: the component draws the text in its colors), *Bounds* -- the text's bounding rectangle, aligned with it -- and *Anchor*, the anchor point. (A definition saved before these outputs were first keeps its wires to Bounds and Anchor.) The component's message says what it shows and where it's anchored (*Markdown, top left*).
- **Preview:** The text in Grasshopper's preview color, code in its syntax colors; green while selected.
- **Bake** (right-click > Bake): Rhino objects, grouped; a token's color is its object's color. Baked Markdown keeps what `MarkdownText`'s parts keep: double-click any of it to edit its Markdown, in place, and its links work. (Links in the preview aren't clickable: bake it.)

**Prompts in Grasshopper** -- the speech-bubble button on Grasshopper's toolbar (right, next to the V° button), or `miniVivisection GrasshopperPrompts`, opens a window with three tabs for the definition on the canvas. It stays above Grasshopper's window and is minimized with it; closing it only hides it, so the chat, Python's namespace and PowerShell keep going.

- **V°Claude:** Claude Code working in the definition. Each message names the definition, whether the solver is on and **the components selected on the canvas** -- select what you mean, then ask ("explain these", "add a loft between these curves and a slider for the count"). What Claude uses:
    - **RhinoAI's Grasshopper tools** (installed and its server running -- see V°Claude in section 6): The whole canvas with every object's wires and messages, the component library, placing components and sliders, wiring, deleting, solving; the Rhino view as an image.
    - **miniVivisection's own**, for what RhinoAI doesn't do: the selection in detail; a parameter's data in full, each item with its facts (a point's coordinates, a curve's length and whether it's closed, a Brep's area, volume and whether it's solid, the bounding box); a script component's code; setting sliders (value, range), Panels (text, *Show as*), toggles, value lists, a parameter's stored values and the Rhino objects it references; writing a script component's code and its inputs and outputs; nicknames, enabled, preview, moving, groups; removing wires; **Markdown notes** next to what it built; an image of the canvas.
    - Claude checks its work -- the components' messages, the data, the canvas image -- before it answers.
- **One undo step per answer:** Whatever one answer changed -- components added, deleted, set, rewired -- is one step in Grasshopper's undo list, named *V°Claude: (your message)*: **Ctrl+Z** takes it all back, Ctrl+Y brings it again; `/undo` in the chat does the same (only when the last step is Claude's). The chat says what changed (*2 changed, 1 added*).
- **Commands:** `/explain` (the selected components, or the whole definition), `/fix` (the components with errors or warnings), `/undo`, `/history`, `/allow on|off` (RhinoAI's commands and scripts), `/new`, `/clear`, `/help`; Tab completes them. One conversation per definition, continued when you come back to it.
- **Without RhinoAI** Claude can read and set, write scripts and notes, but not place, wire or delete components: it says what to do.
- **An answer stays with its definition:** Claude's tools work on the definition the canvas shows; showing another one while Claude answers stops the answer (the chat says so), so that nothing changes the wrong one -- what it did until then is still one undo step in its definition.
- **V°Python:** While a Grasshopper Python component is paused, input runs in its paused frame (as V°Python does in the Script Editor); otherwise in the tab's own namespace, which has `ghdoc()` (the definition, a GH_Document), `ghselected()` (the selected objects), `ghcanvas()` and `ghfind('Name')` (objects by nickname), and `show()`, `hide()`, `clear()`, `bake()`.
- **V°PowerShell:** A PowerShell prompt, started in the definition's folder (Documents for an unsaved one).
- **Settings** (V°Settings and Tools > Options > miniVivisection, tab **Grasshopper**): The toolbar button; each tab on or off (V°Claude also needs the V°AI switch, the others V°Debug); the window stays with Grasshopper; *Claude may change the definition* (*Read and change*, or *Read only*: it explains and proposes in words); *One undo step per answer*; *The selection goes with each message*; *Use RhinoAI's Grasshopper tools*; *Items Claude reads per parameter* (50); *Claude may look at the canvas*; V°Python's helpers; V°PowerShell's folder. Claude Code's path, the model, starting RhinoAI's server and `/allow`'s default are V°Claude's settings (tab *General*, group Claude).

**V°Protect -- a Grasshopper component** (tab *miniVivisection* > *Files*): is a definition, or another file, still the original?

- **No inputs, no outputs:** Its menu sets everything, saved with the definition. *Files*: none set -- the definition's own file; *Add files...* (several at once), *Add this definition*, each file's *Remove*, *Remove all*. Where the originals go: *Archive* -- by default *(the definition's name).protect.zip* next to it; *Choose...* another (an archive that exists is added to), or back to the default -- or **Keep the originals in the definition itself**: no archive; the other files' originals are in the component (a zip, saved with the definition: its file grows by their size), and the definition keeps its own original: Protect saves it once without it -- those bytes are the original -- and once more with them; the file on disk is the original when, loaded, every object's saved state but this original is the same (a fingerprint, MD5 over each object's state, kept with it). *Store now*. A definition not saved yet can't be kept (it says so).
- **Setup** (how it starts): The files are hashed (MD5) and copies stored in the archive, a zip file, whenever the component solves (placed, opened, a setting changed, *Store now*). Inside: the files list (`files.json`: each file's full path, name, hash, size, times) and each copy under its hash -- so two files of the same name in different folders are two entries, a file changed since is replaced (its old copy removed when no other file has it), and an unchanged one left as it is. Its **message balloon** says per file *added*, *replaced*, *unchanged* or *missing* (a missing one as a warning); its tooltip lists the files, the archive and the whole log.
- **Protect** (the button under it, or its menu): The definition is saved and stored as the original -- with the component protecting it, so that the saved file is the original. From then on the component looks like a Grasshopper Button: in front it says **original**, the component green, while the file on disk is the original and the open definition has no changes -- **modified**, the component red, when either isn't so -- then a gray **Revert** button. Its balloon says which (a warning when not the original), and how the other files kept stand; so does its tooltip. Nothing is stored any more. **Right-click anywhere on it** for its menu.
- **Revert** (a click on its button, while *modified*): Asks first; when the file on disk isn't the original, the archived copy is written over it; then the definition is opened again from the file -- the changes of the open one dropped.
- **Back to setup:** Its menu. No password, no write protection: it tells, and puts back.
- **In a Panel's Markdown:** `{{protected}}` shows *protected* or *not protected*, `{{modified}}` *modified*, *not modified* or *not tracked* (not protected) -- the definition's V°Protect's state, following it as it changes --, and a link `[Revert](protect:revert)` is its *Revert* (asked first). V°Text shows them the same way.

**Command `ProtectModel` -- V°Protect for Rhino files.** Is the model still the original? Run it: the command line says the state, then offers what can be done.

- **Setup:** The files kept -- none set: the Rhino file itself; *AddFiles* (several at once), *ClearFiles* -- and where their originals go: *OriginalsIn=Archive* -- by default *(the file's name).protect.zip* next to it, *Archive* chooses another -- or *OriginalsIn=File*: in the file itself (the other files as a zip in it; the model keeps its own original: *Protect* saves it once without it -- those bytes are the original -- and once more with them; the file on disk is the original when, read, every object, table, named view and document string but this original is the same: a fingerprint). *Store* stores the files' originals now (added, replaced, unchanged). Everything is kept in the file's document strings.
- **Protect:** The file is saved and kept as the original. From then on it is *original* while the file on disk is the original and the open model has no changes, *modified* when either isn't so (moving an object, saving a change).
- **Revert** (asked first): The model is closed, its changes dropped; the original is written over the file when that changed; the file opens again. **BackToSetup:** not protected any more; the originals stay as they are.
- **In Markdown text:** `{{protected}}` and `{{modified}}` show the state in the model's Markdown texts -- *protected* / *not protected*, *modified* / *not modified* / *not tracked* --, laid out again when it changes (looked at every 1.5 s while Rhino is idle; that doesn't mark the model changed); `[Revert](protect:revert)` reverts. The example `00_overview.3dm` is protected in itself: move its V° logo, and its line says *modified*.

- The component is `miniVivisection.GH.gha`, built next to the plug-in. At load, the plug-in tells Grasshopper where it is (`miniVivisection.ghlink` in Grasshopper's Libraries folder, if needed); it's there from Grasshopper's next start.

- **FreePause:** While paused, Rhino stays usable. You can select, run commands and use the Gumball. Continue and step with the editor's buttons or keys (F5, F10, F11, Shift+F11, Shift+F5).
- **Drop a folder** anywhere on the Script Editor: it opens in the editor's Explorer (left panel). Files dropped still open as scripts.
- **Command `MarkdownText`:** Markdown as Rhino objects. Run it, type or paste Markdown in its dialog -- with the *Width* text wraps in (mm; 0: no wrapping), the base *Size* (pt: a paragraph's text height, headings larger) and the base *Font* --, and click where its top left goes (the active construction plane). Headings become larger bold text (the first two levels with a line under them), paragraphs wrapped rich text -- **bold**, *italic*, `code` in Consolas, links with a bar under their words (a solid hatch, in the link color) --, lists with bullets, numbers or task boxes (drawn squares, a check mark in the done ones: **click** one to check or uncheck it -- its Markdown changes, the text is drawn again, one undo step), quotes a bar (`|` on each of their lines), code blocks a frame, tables a grid of cells (the header row bold), `---` a line -- all of it as the file's Markdown style says (*Style*, below). It's one group. `-MarkdownText` takes the Markdown from a file (options *Height* and *Width* in model units). Parsed as the Panels' Markdown is (option *Markdown parser*: Rhino's Markdig, or the plug-in's). Example: `examples\00_overview.3dm`, right of the overview.
  - **Editing:** **Double-click** any part of it -- or select it and run `MarkdownText`, or run it and click a part. Its Markdown opens in the dialog: a part double-clicked or clicked (or selected alone, with Ctrl+Shift+click) puts the caret at the start of its section and shows the other parts' Markdown in gray (editable too); the whole text selected opens it all. The whole text is selected in Rhino meanwhile. OK updates the **same objects** in place -- their ids, layers and colors stay; only when the text needs more parts than it has are new ones added (and parts it doesn't need any more removed). **Undo and Redo:** in the dialog Ctrl+Z undoes a word at a time (a step ends at a space, a line break, a tab, a punctuation mark or a pause), back to the Markdown as it opened, Ctrl+Y or Ctrl+Shift+Z redoes; after OK, Rhino's Undo takes the whole edit back -- the objects and their Markdown -- and Redo brings it again.
  - **The parts belong together** by the text's id (user text on each object), not only by the group: ungroup it, and any part still edits the whole text. A copy (Copy, Ctrl+C/V) has its own parts.
  - **Changes in Rhino are taken in:** Before the dialog opens, what was done to the parts with Rhino's own tools goes into the Markdown -- a text's words edited (Rhino's text editor, or *Properties*): put where they came from, the formatting around them kept; the whole text moved, turned or scaled: it stays there; all of a block's parts deleted: its Markdown taken out. A line on top of the dialog (and the command line) says what was taken.
  - **Links:** Click a link to follow it (see *Links in Markdown*); a double-click on it edits, as anywhere on the text.
  - **Style:** How it looks comes from a **Markdown style** -- a small part of CSS: element names (`h1` ... `h6`, `p`, `li`, `task`, `blockquote`, `pre`, `code`, `a`, `table`, `th`, `hr`, `body`) with their sizes in em (one base text height), fonts, weights, colors, the space around blocks, the bullet of each list level (`list-style-type: "\2022" "\25E6"`), the task boxes (`checked: drawn`, or a character such as `"\2611"`; their size), the quote's bar (`bar: "|"`, `line` or `none`), code blocks' frame, tables' grid, and the links' color and line. The default, `styles\markdown_rhino.css` next to the plug-in, lists all it can say. **One style per Rhino file**, kept in it: a file starts with V°Settings > Markdown > *Markdown style for Rhino* (empty: the default) and keeps a copy with its first Markdown text. In the dialog, the line above *Width* says which style the file has: *Edit style...* opens it in a small editor (what it doesn't understand is shown as you type), *Load...* takes a style file, *Save as...* writes it as a file of your own, *Default* goes back to miniVivisection's -- OK then draws **all** of the file's Markdown texts with it. A file whose style is an untouched copy of a default -- of any version -- gets the current default when it's opened, its texts drawn again; a style of your own never changes by itself. V°Text draws with the active Rhino file's style. Grasshopper's Panels have their own: *Markdown style for Grasshopper* (`styles\markdown_grasshopper.css`; em there is the Panel's font size). Both settings have *Edit*, the same small editor: a default is read-only -- *Save as* makes your own, and the setting then points to it.
- **Links in Markdown** (Panels, `MarkdownText`, V°Text): `[text](target)`, the target one of
  - `gh:Name` -- a Grasshopper object, by its nickname (or name, or instance id; a group by its name too): the canvas glides to center it, and a red circle marks it for a moment (the active definition first, then the other open ones);
  - `ghview:Name` -- a named view of the Grasshopper canvas (View > Named Views), restored;
  - `rhino:Name` -- a Rhino object, by its name (or id): the view zooms so it takes about a tenth of the view, its surroundings in sight (V°Settings > Markdown > *Links to Rhino objects: their size in the view (%)*, 10 by default; 100 fills the view), and a red circle marks it;
  - `rhinoview:Name` -- a named view of Rhino's (NamedView), restored in the active viewport -- or, when there's none of that name, the viewport with that title (`rhinoview:Perspective`) made the active one;
  - `script:file.py` -- a script (`.py`, `.cs`) or a Markdown file (`.md`) opened in the Script Editor, not run (an open one is shown);
  - `protect:revert` -- the protected original put back: in Rhino `ProtectModel`'s *Revert*, in a Panel its definition's V°Protect's (asked first);
  - `https://...`, `mailto:...`, `file:...` -- the browser or the app for it.

  **Their look:** links are blue -- the Markdown style's `a { color: #0066CC; }` (a name such as `RoyalBlue`, `#RRGGBB` or `rgb(r, g, b)`), while V°Settings > Markdown > *Markdown links in color* is on. A link's words and the **line under them** are in the link color; the line is as long as the link's words, `text-decoration-thickness` high (10 % of the text height), its top `text-underline-offset` under the baseline (15 %, an underline's place; about 30 % clears the descenders of g, p, y); `text-decoration: none` leaves it out. In Rhino (`MarkdownText`, V°Text) the line is a solid hatch, one under each line of the link -- where Rhino wraps it, and at a hard line break in it; it belongs to the text: it moves, edits and bakes with it (V°Text: in *Decorators*). A Rhino text object has one color, so the plug-in **draws** the link's letters over it, filled in the link color -- drawn, not objects: a click on a link's word still picks just the text (not while the text is selected, nor after its words were changed in Rhino until it's edited again). Off: the line in the text's color, by its layer.

  **Into another file -- from Rhino to Grasshopper and back:** put the file before the name, with `#`: `gh:grasshopper/gh11_markdown_notes.gh#Ring` opens that definition in Grasshopper when it isn't open (starting Grasshopper when it isn't running), puts it on the canvas and goes to *Ring*; `ghview:file.gh#View` likewise; `rhino:../00_overview.3dm#Logo` opens that model in Rhino when it isn't the one open (asking to save yours first) and zooms to the objects named *Logo*; `rhinoview:file.3dm#View` likewise. The file alone (`gh:file.gh`) just opens it. A relative path is from the file holding the link -- the .3dm for Markdown text in Rhino, the .gh for a Panel -- so save that file first. The examples link both ways: `00_overview.3dm` into GH 11, GH 11 into `00_overview.3dm`.

  **A file without a scheme** is a link too: `[next lesson](gh3_stop_a_hang.gh)` opens that definition (or shows it, when it's open), `[the model](../00_overview.3dm)` that model, `[lesson 1](../01_watch_geometry.py)` that script in the Script Editor -- the same as `gh:`, `rhino:` and `script:` with the file alone; a full path (`C:\models\a.gh`) works as well. The Grasshopper lessons end with such links to the one before and after, and to the overview.

  A name with spaces: `[the twist](<gh:My Twist>)` or `gh:My%20Twist`. **Click** the link, in a Panel shown as Markdown and in Rhino alike -- V°Settings > Markdown > *Markdown links: follow with*: *Click* (the default: a plain click, once the double-click time has passed), *Ctrl+click* (a plain click selects) or *Off*. A double-click edits, on a link too. Over a link, a hint by the mouse says where it goes and how to follow it (off: where to switch it on); in a Panel the pointer becomes a hand. A target not found is said on Rhino's command line.
- **Command `miniVivisection`:** Quick switches (Draw, FreePause, HoverPreview, WatchExpressions), plus BreakNow, WhereIsEveryone, StopPaused (while one is paused: stops every paused script, e.g. when its editor can't be reached), BakeAll, StopEditing (while objects are edited), GrasshopperPrompts (the prompts window), Settings and LogFolder.
- **Logs:** `%TEMP%\rhinovivisection\minivivisection` holds `minivivisection.log` (detailed; level set in the settings) and `user.log`; the last session's are `*.previous.log`. A session that ended without Rhino shutting down (a crash) keeps its detailed log as `minivivisection.crashed-(time).log` (the last five), and V°Claude's steps in Grasshopper are written at once -- the last thing before a crash is in it.
- **Limits:** Experimental; it relies on Rhino 8's internal editor code, so a Rhino update can break parts. Inline values, tooltips with scope, the Python tab and Edit in Rhino are for Python 3 scripts only. IronPython 2 scripts (`#! python2`) get the debugger features, drawing of plain names and conditional breakpoints (written like `i > 3 and name == 'a'`: and/or/not, True/False/None). While one is being debugged, a notice on top of V°Python and V°Claude says that their Python 3 can't reach its variables.
